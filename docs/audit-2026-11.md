# Product audit — start of functional development (2026-10-31)

Written when the owner approved the UI direction and asked for functional
development (R37). It records what exists, what is real, what is simulated,
what is missing, and what the operating systems limit. It also records the
Freedom research and the resulting architecture adjustments. Milestone
acceptance criteria are in `docs/milestones.md`.

Evidence words are used strictly:
**Verified** = observed working in a named environment.
**Implemented** = code exists and compiles and/or passes unit tests, but it was not observed doing its job where it matters.
**UI-only** = a screen or a labelled demo, with no working mechanism behind it.
**Missing** = nothing exists yet.
**OS-limited** = the platform caps what can be done.

### Limited by the operating system (verified against current documentation)

| Limit | Consequence |
|---|---|
| **Android has no public API that stops a third-party app from launching** without device-owner/MDM control | Android blocking is **detect-then-cover**: usage access sees the foreground app and Lockd In brings its block screen to the front. The app has started but is moved behind the block screen; it is not closed. Typical detection lag is up to ~1 s (to be measured). |
| Background activity starts need an exemption; the documented one we rely on is "Display over other apps" (SYSTEM_ALERT_WINDOW) | Required permission. Without it, blocking degrades to a notification and is reported as **Permission needed**, never Protected. |
| Usage access is a special app-op the user grants in Settings | Required permission. It can be revoked at any time, so we re-check every few seconds and report the loss. |
| AccessibilityService: Play restricts non-accessibility uses; Android's **Advanced Protection Mode** (Android 16+/17) only lets apps whose core purpose is accessibility use it (Malwarebytes, Mar 2026) | Accessibility stays **off** in Play builds (E10). Usage access is the default. Freedom's Android blocking relies on accessibility and is exposed to this. |
| `QUERY_ALL_PACKAGES` is restricted on Play to apps whose core purpose needs it | The app picker lists **launchable apps** through a targeted `<queries>` block (MAIN/LAUNCHER intent). This is enough to choose apps to block. |
| Exact alarms: `SCHEDULE_EXACT_ALARM` is denied by default for new installs on Android 14+; `USE_EXACT_ALARM` is only for alarm-clock and calendar apps | Scheduled starts use `setExactAndAllowWhileIdle` when the user grants exact alarms. Otherwise they use `setWindow` (≥ 10 min window), and the UI says starts may be late. Never `USE_EXACT_ALARM`. |
| Foreground service type `specialUse` needs a Play declaration and justification | Declared, with subtype "user-started focus session". Covered in the Play kit. |
| Android has no system-wide website blocking without VPN/DNS | **No VPN (owner).** Websites are covered by blocking the **browser app** during focus, or by a later browser extension. Android cannot block a site inside an allowed browser, and the product says so. |
| Windows: per-user code cannot stop an elevated app or prevent launches | The per-user agent can minimize and mute only, after launch. Prevention needs App Control/AppLocker through an admin-installed service (U1/U3). It is VM-tested first. |
| Windows Smart App Control / Android Auto Blocker | Real-device testing needs **signed Windows binaries** and **Play internal testing**. Both are owner setups (§5). |

## 2. Existing decisions kept

- Rust core for timing rules, with ports checked by parity vectors (ADR-0001, E13).
- Native shells: WinUI 3 + WebView2 on Windows; Compose on Android (ADR-0002).
- Account-free device-group pairing over an encrypted relay (ADR-0005; owner U6/U12 still open).
- Never terminate real apps (R12).
- Overrides are delayed and scoped; emergency recovery is immediate and separate (core).
- A peer that has not reported is "Unknown", never Protected (ADR-0008).
- Honest lock: the shackle closes only while restriction is verified on that device (R36).
- Usage access by default; accessibility left out of Play builds (E10).

## 3. Freedom: what it does, and where Lockd In can be better

**Verified from Freedom's own pages** (freedom.to, help.freedom.to):

- Platforms: Mac, Windows, iOS, Android and ChromeOS.
- Blocklists and a website allowlist ("exceptions"). Exceptions are available on Mac and Windows only.
- Scheduled and recurring sessions; recurring is a premium feature.
- **Locked Mode**: no ending or editing a session early. The dashboard allows one early end per 7 days. iOS has gaps.
- Windows site blocking: a browser-based mode by default with a system-proxy fallback. It documents a 1–2 s delay, apps losing connectivity under the proxy, and caveats for embedded YouTube.
- Android blocking uses the accessibility service. Its help pages describe battery-optimizer and cleaner apps disabling it.
- Session history, the Insight browser extension and focus sounds.

**From recent reviews** (Trustpilot, 14 recent reviews at about 2.6/5). These are individual reports, not verified behavior:

- Bypass through safe mode, permission toggles or another browser.
- Free-tier limits and upsell pressure.
- Billing and renewal complaints.
- A Windows app that would not open.
- Slow development.
- Praise for genuine habit change.

**Opportunities.** Each one is something we can actually deliver:

1. **Honest protection state.** Freedom's main complaint is silent bypass. We show *Protecting / Permission needed / Offline / Unknown* per device and never imply protection we did not verify (already a core invariant).
2. **Breaks inside a session.** Focus and break rounds are first-class. Restrictions lift for the break and come back on their own.
3. **Explicit, humane commitment.** Choose a commitment level up front: Flexible, Delayed (countdown), or Locked (only emergency recovery). Emergency recovery is always available and logged, never hidden.
4. **Task-first start.** "What are you working on?", a first small action and saved resources. Freedom starts from a blocklist; we start from the work.
5. **Android without accessibility.** Usage access + block screen survives Advanced Protection and avoids accessibility-policy risk. The trade-off is up to about a second of detection lag, stated plainly.
6. **No proxy or VPN.** Other apps never lose their network because of us.
7. **Local-first, account-free.** Nothing to bill or breach on a server for single-device use.

We do not copy Freedom's names, Locked Mode wording, branding or pricing. We do not promise iOS, ChromeOS or Mac.

## 4. Architecture adjustments

1. **Android enforcement moves from probe to product (M1).**
   - New `enforce` package in the app:
     - `FocusService`: a `specialUse` foreground service that runs independently of the UI and re-evaluates the persisted session with the ported core rules.
     - Usage-events detector.
     - `BlockActivity`: block screen with the current task, time to the next break, Return to work, and the override route.
     - Capability checks every 5 s.
     - Boot and package-replaced receivers that restart a still-active session.
   - Rules are **per profile, per device**: blocked packages (Block list) or allowed packages (Approved only).
   - System essentials are always allowed: the dialer, emergency, settings, the launcher, the keyboard and Lockd In itself.
2. **The blocking decision is a pure function** (`BlockPolicy.decide`), unit-tested on the JVM. The service only gathers inputs and acts. The same table is used later for Windows.
3. **Truthful status from the enforcer.** The service publishes `Protecting` only while restriction is due, permissions are present and the service is alive. It publishes `PermissionNeeded` otherwise, and `NotRestricting` on breaks and timer-only sessions. The Compose UI's lock closes only on `Protecting`.
4. **State v2 with a migration.** This adds per-profile app rules, the commitment level and the session's rule snapshot, so editing a profile mid-session does not change the running session. v1 data upgrades in place.
5. **Commitment levels.** The core already supports delayed overrides; the levels map onto it:
   - Flexible = end any time.
   - Delayed = 90 s countdown (U5 default).
   - Locked = no override, emergency recovery only.
6. **Windows.** Ship the per-user agent (minimize + mute, post-launch, honestly named) in the product first. Prevention through App Control stays behind the VM go criteria and U1/U3. The Windows agent runs as a separate process from the UI, so closing the window does not end blocking.
7. **Websites.**
   - Android: block browsers as apps.
   - Windows (M1): block browser apps or windows only.
   - A companion browser extension for site-level rules follows in M1b/M2, after store review.
   - No proxy, no VPN, no hosts-file edits.
8. **Web app role.** Planner and remote control for paired devices (M2). It never shows Protected for itself.

### Update 2026-11-01 (R38)
After comparing with Freedom's Android setup, the owner chose to offer **Accessibility detection now**. It is optional, is recommended in setup, and is opened only after an in-app disclosure.
- It covers apps instantly and blocks websites by domain in major browsers.
- Usage access + display over other apps remains the automatic fallback.
- The Play submission will need the Accessibility declaration and a demo video.
- Advanced Protection users fall back to usage access (no website blocking).
